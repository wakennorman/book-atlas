# 债一 B2 · 拆分 `bindUI()` 的方案（v0.197）

## 一、为什么要拆

`bindUI()` **503 行**（L5607–L6109），占 `app.js` 的 8%，是**全文件唯一超过 400 行的函数**
（其余最大 139 行 `loadBook` / 136 行 `initChart`）。它把 28 个互不相干的控件绑定堆在一起：

> ⚠ **更正**：我在 v0.194 的体检报告里写过「`buildOption` 350 行、`applyEdgeFilter` 306 行、
> `epubPage` 219 行」—— **那三个数全是错的**。当时用的是「从函数声明行数到下一个顶层符号」
> 这种粗略算法，而箭头函数（`const x = (…) => …`）本身没有大括号，于是被算成了几百行。
> 用括号配平重算后：这三个真实长度分别是 **1 / 7 / 9 行**。
> ⇒ **只有 `bindUI` 一个真问题**，不是三个。这个错误是 v0.197 新写的
>   `test/app-func-size-guard.mjs` 当场逮住的 —— 它自己也踩了同一个坑两次（见该文件头）。

## 二、切分点是怎么定的（**机械判定，不是拍脑袋**）

我扫了 `bindUI` 内所有 `const`/`let` 声明（**35 个局部变量**），
再看每个注释块引用了哪些：

> **结论：35 个局部变量里，34 个只在「声明它的那一块」内被用到。**
> **唯一的例外是 `clearQueryInputs`**（L5659 定义 → L5892 / L5894 使用，跨了 3 块）。

⇒ 这就是切分依据：**一个局部变量被引用到的所有块，必须放进同一个函数。**

⚠ 顺带核实：`graphEl` 看着跨块（L6049 定义、L6050 用），但 L6026 那个是
**另一个函数内的同名局部变量**（`initChart` 里的），互不相干 —— 名字相同 ≠ 同一个变量。

### `clearQueryInputs` 怎么办

它是唯一跨块的（被 1 和 6 都要用）。

**方案：提为顶层函数 `clearQueryInputs()`。** 它本来就是纯 DOM 操作、
不依赖 `bindUI` 的任何局部状态 ⇒ 提到顶层作用域后，两个函数都能调。

⚠ **这是本轮唯一一处"改变了作用域"的动作**，也是唯一有真实风险的点。
所以判据里为它单列一条（见下）。

### `bindUI()` 本身

缩成 8 行：

```js
function bindUI() {
  bindSearchUI();
  bindPlaceFilterUI();
  bindSizeFilterUI();
  bindPanelDelegates();
  bindEdgeFilterUI();
  bindViewControls();
  bindChapterTimeUI();
  bindExportAiUI();
}
```

## 三、验收判据（每条都要能红）

| # | 判据 | 怎么验 |
|---|---|---|
| 1 | `app.js` 语法完好 | `node --check js/app.js` |
| 2 | **顶层符号只多不少**（原 251 + 8 新 − 1 移出 = 258） | 写进 `test/app-partitions-guard.mjs` 的对照 |
| 3 | **`bindUI` 不超过 20 行** | 同上，守卫里加一条"app.js 不得有 > 400 行的函数" |
| 4 | **剥离后逻辑逐字不变** | 脚本自检：把 8 个新函数的函数体按原顺序拼回去，应当与原文**逐行相同** |
| 5 | 门禁全绿 | 尤其 `test/layout-stable.mjs` / `lock.mjs`（视口相关） |
| 6 | 浏览器测试 | `e2e` / `relations` / `lock` / `layout-stable` / `roam` |

⚠ **第 4 条是关键**：它证明"我只是把代码搬到了别的函数里，没改任何一行"。
这比任何"看起来对"都强 —— 拆分最容易出的错就是**手滑改了一个字符**。

## 四、⚠ 已知的三个坑（动手前先知道）

### 1. 局部变量的**声明提升**问题
`bindUI` 里的 `const` 是**块级作用域**。拆成独立函数后，
如果 A 块用了 B 块声明的变量（原代码里靠"声明在前"侥幸能用），
拆完就变成 `ReferenceError`。

**排查方式**：脚本已算出 34/35 的局部变量都在本块内，
唯一的例外 `clearQueryInputs` 提到顶层。⇒ **不会有这个问题**，
但拆完仍要用 `node --check` + 浏览器测试各验一遍。

### 2. **`addEventListener` 的执行顺序会变**
原来 515 行是**顺序执行**的；拆成 8 个函数后，只要调用顺序不变，行为一致。
⇒ `bindUI()` 里的 8 次调用**必须按原分块顺序**排。
⚠ 若某个块依赖另一个块**已经注册**的委托（document 级委托是后注册的会盖掉先注册的），
顺序错了会静默失效 —— 这类错**不会报错**，只表现为"点了没反应"。
⇒ 所以判据 5/6 的浏览器测试必须真跑，不能只看语法。

### 3. 别在这轮里"顺手优化"
本轮**只搬代码**。看到写着 `v85`、`v89`、`v93` 的老注释、看到能简化的写法 ——
**都不动**。重构和清理混在一起，review 就没意义了。

## 五、顺序

1. 先加守卫（第 3 条：不得有 > 400 行的函数）—— 让它**先红**
2. 写拆分脚本（带判据 4 的"拼回去逐行比对"自检）
3. 跑守卫 + 门禁 + 浏览器测试
4. 单独提交

⚠ 每一步单独提交，不许把「加守卫」和「拆函数」混在一个 commit ——
否则 diff 大到没法 review，而 review 恰恰是防止重构引入回归的唯一手段。
