# book-atlas · 方案评估（2026-09-20）

> 目的：为"可复用的小说人物关系图谱 + 事件时间轴"项目选定技术路线。
> 结论先行：**用「数据 + 渲染」分离的纯静态方案**；story-graph 只做参考，不做数据源。

---

## 1. story-graph 拆解：它的「书源」到底是什么？（用户问题的答案）

**答案：没有书源。** 它把书名直接发给 DeepSeek，让模型凭自己的记忆一次性写出 JSON。

代码证据（已下载源码，`research/story-graph/`）：

| 位置 | 事实 |
|---|---|
| `server.js` → `POST /api/generate` | 只接收一个字符串 `novelName`，直接请求 `https://api.deepseek.com/v1/chat/completions`，模型 `deepseek-chat`，temperature 0.7，max_tokens 8192，用固定 system prompt 要求输出 JSON |
| `index.html` → `callDeepSeekDirect()` | 还有"浏览器直连"模式：同样的 prompt 直接从浏览器打 DeepSeek，Key 存 sessionStorage |
| `server.js` → `cache/<书名>.json` | 只是**生成结果的缓存**（同名书不重复生成），不是书源 |
| `index.html` line 524 | 唯一的"内置数据"是硬编码的《三国演义》示例，用来演示 UI |
| 全文检索 | 无原文、无检索（RAG）、无内置书库、无联网查资料 |

**生成规格**：20–35 个人物、3–6 阵营、30–60 条关系、8–14 个事件；关系只有"类型"一个字符串，事件只有 name / summary / chars，`year` 可为 null。

**对我们的四个硬伤**：

1. 数据来自模型记忆 → 你踩过的坑（阿尔卡蒂奥 vs 何塞·阿尔卡蒂奥）它必然重犯；
2. 《百年孤独》书里没有年份 → 它的事件时间轴（按 year 排）会失效或乱编；
3. 没有"定义关系的小事件"这一层（我们要的就是这个）；
4. "两人什么关系"= 把全部数据塞进 prompt 让 LLM 回答，不是图查询，会编；
5. 需要 Express 服务器或浏览器直连（Key 暴露在前端），不是纯静态。

**值得借鉴的部分（MIT 许可）**：交互清单（力导向图 + 底部时间轴 + 点击高亮 + 双人路径 + 导出 PNG + 拖动编辑 + 暗色主题 + 移动端断点 1024/768/480）、JSON 结构雏形、缓存思路、i18n 思路。

## 2. 候选方案对比

| 方案 | 数据来源 | 数据质量 | 多端 | 成本 | 判断 |
|---|---|---|---|---|---|
| A. 纯静态 + 人工校对 JSON（推荐） | 我们（AI 出草稿 + 人工/我校对） | ★★★ | ★★★ 部署后手机/平板/电脑都能开，可 PWA 离线 | 中 | ✅ 主方案 |
| B. story-graph 直接用 | LLM 凭记忆 | ★ 对复杂小说不可信 | ★ 需要 Node 服务或直连 Key | 低 | ❌ 不满足精度 |
| C. story-graph 改造（换成本地 LLM、AI 只出草稿） | LLM + 人工 | ★★ | ★★ | 中低 | 可做过渡，不如 A 干净 |

**结论**：走 A。LLM 只当"打字员"，最终数据必须落 JSON 并校对；查询用图算法本地算。

## 3. 推荐架构（book-atlas）

```
book-atlas/
├── books/<slug>/book.json      # 每本书的数据（可复用核心）
├── app/                        # 静态前端（响应式 + PWA）
├── scripts/                    # draft.mjs（AI 草稿）· validate.mjs（校验）· build.mjs
├── assets/                     # 参考图/图标（含已下载的家族树）
├── research/                   # 外部项目研究（story-graph 等）
└── docs/                       # 方案与规范
```

### 数据 schema（草案 v0.1，每本书一份 JSON）

- `meta`：书名 / 作者 / 译本 / 语言 / license / sources[]
- `characters[]`：`id`（拼音 slug）、`name`、`aliases[]`、`generation`（第几代）、`faction`、`desc`、`fate`
- `relations[]`：`from`、`to`、`type`（父子/夫妻/情人/仇敌/师徒…）、`style`、**`events[]`（定义这段关系的小事件：text + 章节 + 可核出处）**
- `events[]`：`id`、`phase`（阶段而不是年份）、`order`、`name`、`chars[]`、`summary`、`impact`、`quote?`
- 对《百年孤独》这种没有年份的书：时间轴用 **phase + order**（建村 → 吉普赛/失眠症 → 教堂与婚礼 → 内战 → 停战与金鱼 → 铁路/香蕉公司 → 大雨 → 飓风），而不是假年份。

### 渲染层选型

| 库 | 许可 | 优势 | 用途 |
|---|---|---|---|
| **ECharts**（主推） | Apache-2.0 | 中文文档最全、移动端自适应好、graph 力导向 + 时间轴/自定义系列一库搞定 | 主视图：关系网络 + 事件轴 |
| vis-network + vis-timeline | 需核对双许可 | story-graph 同款、上手快、API 简单 | 备选/快速原型 |
| family-chart（d3） | MIT | 家谱专用（生命线时间轴 + 婚姻标记），可做"家谱视图" | 可选第二视图 |

### "两人什么关系"

本地 **BFS 最短路径** 直接在图数据里算 → 返回路径上每一跳的「关系 + 定义该关系的小事件」。LLM 只在最后可选地把它润色成一句话（可关、可离线）。**不把数据交给 LLM 回答**。

### 多端与部署

- 静态站 + PWA（`manifest` + service worker）：手机可"添加到主屏幕"，离线可看；
- 响应式断点（参考 1024/768/480）；
- 部署：GitHub Pages 或 Cloudflare Pages（免费）；数据 JSON 在仓库里，手机看图、电脑改数据；
- 阅读笔记继续放 Second Brain（`02_文学语文/阅读/<书名>/`），两边共用同一套人物 id 对应。

### 数据生产管线（复用性关键）

1. `draft.mjs`：输入书名/章节文本 → 让 LLM 产出符合 schema 的草稿（有原文就切段喂原文，没有就让它列已知资料）；
2. 人工校对（重点：重名消歧、关系方向、小事件出处）；
3. `validate.mjs`：schema 校验 + 一致性检查（悬空引用、重名、无关系孤点、事件引用不存在的人物）。
